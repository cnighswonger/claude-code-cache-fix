# Review: upstream change detection directive

Date: 2026-04-25
Reviewed: `docs/directives/proxy-upstream-change-detection.md`
Label applied: `changes-requested`

## What Is Correct

- The feature is appropriately scoped as a read-only detection layer for v3.2.0, and deferring remote telemetry until a separate privacy review is the right boundary for this release ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L28), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L37)).
- Placing the extension early in `onRequest()` is consistent with the existing proxy pipeline: if the goal is to detect what Claude Code actually sent before any cache-fix mutation runs, ordering it before the mutating request extensions is the correct design choice ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L42), [proxy/pipeline.mjs](proxy/pipeline.mjs#L49)).
- Persisting the baseline with `tmp + rename` is the right high-level contract for the baseline JSON file. That matches the working pattern already used by the proxy diagnostics that need torn-write protection ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L123)).
- The directive correctly recognizes that proxy hot-reload changes the state model relative to preload-era diagnostics, and it attempts to address that with a persisted per-namespace baseline rather than module-lifetime-only memory ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L31), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L143)).

## Blockers

- The activation model is internally contradictory and does not work with the current loader. The directive says the diagnostic is activated by `CACHE_FIX_UPSTREAM_DETECTION=1`, but it also says to add an `extensions.json` entry with `enabled: false` ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L147), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L189), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L204)). In this repo, disabled extensions are not loaded at all, so an env var inside the module can never take effect if config disables the module first ([proxy/pipeline.mjs](proxy/pipeline.mjs#L24)). The directive needs to pick one valid pattern: `enabled: true` plus runtime env gating like `prefix-diff`, or `enabled: false` plus explicit config opt-in.
- The proposed fingerprint is not verifiably content-free. `system.block_role_markers` is derived by parsing the first ~80 characters of each system block, and `messages.system_reminder_patterns_seen` is built by extracting tags from arbitrary message text ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L69), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L83), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L96), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L98)). That contradicts the review checklist requirement that the fingerprint contain no prompt text, no file paths, and no message bodies ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L194)). If the design wants those signals, it needs a closed allowlist or a hash-only representation that cannot echo user or prompt content.
- The fingerprint equality semantics are inconsistent. The proposed fingerprint object includes a per-call `timestamp`, but the directive also requires identical fingerprints across timestamp drift and says "if fingerprint matches baseline -> no-op" ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L61), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L105), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L167)). As written, a literal fingerprint comparison would differ on every call. The directive needs to separate event metadata timestamps from the structural fingerprint payload, or specify an exact comparator that excludes volatile fields.
- The JSONL atomicity contract is asserted but not specified in a way that is defensible. The checklist and test plan require "atomic-append" behavior for `upstream-changes.jsonl`, but the directive never names a concrete mechanism or guarantee equivalent to the baseline file's `tmp + rename` contract ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L180), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L198)). For concurrent `onRequest()` calls, "append JSONL and hope it is atomic" is not enough for a directive-level correctness claim. The design needs to either cite a real bounded append guarantee it intends to rely on, or switch to a write pattern that actually provides atomic record publication.

## What Needs Attention

- Lifecycle/state ownership needs to be spelled out more precisely. The directive says to keep an in-memory baseline per namespace and also to read the persisted baseline "on extension load," but it does not say exactly which module-level state exists, when hot-reload resets it, or whether the throttle window is also persisted or intentionally process-local ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L31), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L121), [docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L143)). That is fixable, but the implementation handoff will be cleaner if the hook lifecycle is explicit.
- The throttle is plausible as defense-in-depth, but it adds another time-window state machine to what is otherwise a local diagnostic. For v3.2.0, this may be more complexity than necessary unless there is evidence that false alert storms are a realistic operational problem.
- The file path in the "Files modified / created" table uses `tests/upstream-change-detection.test.mjs`, but this repo’s test suite lives under `test/` ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L188)).
- The atomic-write test description uses "tmp file collision" to simulate a mid-write failure ([docs/directives/proxy-upstream-change-detection.md](docs/directives/proxy-upstream-change-detection.md#L176)). That does not actually validate the `rename`-based atomicity contract described for the baseline file, and it will be brittle if the implementation uses unique temp paths as the other extensions do.

## Recommendations

- Resolve the activation model before implementation. The least surprising option here is the `prefix-diff` pattern: module `enabled: true`, runtime no-op unless `CACHE_FIX_UPSTREAM_DETECTION=1`, and no disabling entry added to `proxy/extensions.json`.
- Redesign the fingerprint schema so every persisted field is mechanically content-free. Counts, positions, booleans, bucket labels, and hashes of stable identifiers are fine. Parsed section names and arbitrary `<...>` tags from message text are not.
- Move timestamps out of the fingerprint object and into the emitted event records (`baseline_established`, `structural_change`, `alert_storm`). Then define fingerprint equality as a straight structural comparison of the persisted fingerprint payload.
- Replace the vague JSONL "atomic append" requirement with a concrete write contract. If the team wants per-event JSONL, the directive should specify exactly how concurrent writers avoid interleaving; otherwise, switch alerts to the same atomic replace pattern used for baseline state.
- Tighten the lifecycle section so it explicitly says:
  `on module load`: best-effort read baseline file into in-memory map;
  `onRequest`: compute fingerprint from `ctx.body`, compare against in-memory baseline for the namespace, emit event if changed, atomically persist new baseline, update in-memory map;
  `hot reload`: in-memory map resets, baseline file repopulates it on next module load.
- Fix the test path to `test/proxy-upstream-change-detection.test.mjs` or whatever final `test/` path the implementation will actually use.

## Bottom Line

Revise before implementation. The feature is valuable and the high-level direction is right for v3.2.0, but the current directive still has four blocking design problems: its activation plan does not work with the actual extension loader, the proposed fingerprint is not truly content-free, the fingerprint equality semantics conflict with the included timestamp field, and the JSONL atomicity requirement is asserted without a concrete mechanism. Once those are tightened, this should be a straightforward directive to approve.
