# PR #215 — Workflow-tool agent-id header synthesis directive — round 1 (Fable)

Reviewed at HEAD `387bcf8` (directive stage, no implementation yet). Verified against `proxy/pipeline.mjs`, `proxy/server.mjs`, `proxy/upstream.mjs`, `proxy/stream.mjs`, `proxy/extensions/{usage-log,request-log,cache-telemetry,deferred-tools-restore}.mjs`, `proxy/extensions.json`, `claude-code-meter/src/log/schema.mjs`, the PR #213 round-1/round-2 Fable reviews, and `playbook_cc_binary_inspection.md`.

## What Is Correct

- The gap is real and well-sourced. CC#66761's load-bearing distinguisher — Task subagents carry `x-claude-code-agent-id`, Workflow-spawned agents carry only the parent's session id — is accurately described, and "closed upstream, non-retroactive, operators have a visibility gap today" is a legitimate motivation for a proxy-side derived key.
- The derived-not-authoritative framing is the right posture: explicit `derived-` prefix, canonical-wins read priority, self-retiring design once CC backfills the canonical header. Condition 2 (canonical id **absent**) structurally prevents derived ids from ever shadowing canonical ones, and the Task-subagent integration test pins that.
- Deterministic, stateless derivation (no cross-request memory, fresh boot reproduces the same ids) is the correct shape for this problem and avoids the persistence questions entirely. The deferred-scope list (no backfill, no cross-tool, no restart persistence) is well judged.
- Fail-open on no-marker-detected (`undefined` → behavior unchanged) matches the proxy's established safety posture.
- Two consumers (usage-log + request-log) legitimately satisfies the repo's 2+-call-sites rule for a shared helper module — the *module* is justified (its home is not; see B4).
- `playbook_cc_binary_inspection.md` exists and is a real, current technique doc (npm tarball + `strings`, sha256 citation discipline) — the provenance *method* the directive leans on is sound (the catalog content is not; see B5).
- The env-var-off integration test ("behavior matches current state") and the Task-subagent negative test are the right regression anchors.

## Blockers

**B1. Request-header synthesis is architecturally impossible through the existing pipeline, and no component owns it.** The directive's Synthesis section says the derived headers are added "to the request headers (visible to upstream)." Verified against the request path: `preForward` hands extensions a *copy* of the client headers (`{ headers: { ...clientReq.headers } }`, `server.mjs:86`) and after `runOnRequest` only `reqCtx.body` is re-serialized into `forwardBody` (`server.mjs:97-99`); header mutations are discarded. `forwardRequest` then rebuilds upstream headers from the original `clientReq.headers` (`server.mjs:132-136`, `upstream.mjs:204`). So nothing an extension — let alone a passive `proxy/lib/` module — writes to headers ever reaches Anthropic. Making the header "visible to upstream" requires plumbing changes to `server.mjs`/`upstream.mjs` that the Files-modified list does not declare. Compounding this, no component owns the derivation at request time: lib modules have no hooks (`loadExtensions` only loads `proxy/extensions/*.mjs`, `pipeline.mjs:15-31`); `usage-log` has no `onRequest` hook and at `onStreamEvent` time has no access to request headers or body (`usage-log.mjs:273-319`; the stream ctx carries `event/meta/telemetry/responseHeaders` only, `stream.mjs:63`); `request-log`'s `onRequest` doesn't see the system prompt parse the directive needs. The fix is to drop upstream visibility entirely: run the derivation in an `onRequest` hook (owned by a named extension), stash the result on `ctx.meta` — the exact `cache-telemetry` pattern the codebase already documents for this problem (`cache-telemetry.mjs:170-179`) — and let usage-log/request-log read `ctx.meta`. The attribution surfaces the Goal section names (usage-log rows, event log) are all in-proxy; nothing here needs to go upstream. This also dissolves blocker-adjacent point 7 ("no request mutation" while adding request headers is a self-contradiction — see Attention 1).

**B2. The meter-schema claim is false, and default-on breaks every unpatched meter install.** The directive asserts "the schema field on the meter side does not need to change: it remains `agent_id` (optional), and the source field documents whether the value is canonical." Verified against `claude-code-meter/src/log/schema.mjs`: `MeterRowSchema` is `z.strictObject` (line 5) and has **no `agent_id` field and no `source` field** — neither exists today. Emitting either on a usage-log row makes every current meter install reject the row, because strict-object validation rejects unknown keys. This is precisely the hazard the repo just navigated for `request_id`: cache-fix v4.1.0 shipped it **default-off** specifically because "older meter installs reject rows that carry it" (`usage-log.mjs:40-44`, schema.mjs:42-48), with the default flip deferred until the meter floor was established. PR #215 proposes default-on in the same release while describing the companion meter PR as merely "document the `source` value" — it is actually a schema change, and the release ordering (meter schema first, then cache-fix emission, gated default-off until the meter floor exists) must be stated. As written, v4.2.0 ships a row format that the entire installed meter base rejects.

**B3. The derived id cannot satisfy the directive's own acceptance test.** `derived_agent_id = sha256(session_id + marker_substring + shape_signature)` where `shape_signature = hash(tools[*].name sorted)`. The integration fixture is "a Workflow `parallel()` fan-out → 3 subagent calls; assert all three carry distinct `derived-agent-id`." Walk it through: three parallel legs running the same agent type carry the same session id (per CC#66761, the parent's), plausibly the same marker (same `<workflow-agent-context>` sentinel — the marker identifies *Workflow-ness*, not the leg), and the same tools list (same agent type → same tool set). All three inputs identical → all three ids identical → the headline test fails by construction. The directive needs a per-leg discriminator (agent name/prompt-digest from inside the marker block, fan-out index if present in the context block — whatever binary inspection shows is actually in there) and must state which input provides leg-distinctness. The stability half of the claim is also shakier than stated: the codebase's own `deferred-tools-restore` extension documents that CC's tools list collapses from ~40 tools to "a handful of CC built-ins" and back across turns of the same session (MCP reconnect race, `deferred-tools-restore.mjs:1-10`) — so `tools[*].name` is *not* invariant across consecutive turns of the same leg, and one reconnect race splits one leg's traffic across two derived ids. Either the signature input must be hardened (e.g., exclude MCP tools, or hash only built-ins) or the instability must be documented as accepted. Right now both halves of "distinct across legs, stable within a leg" are unsupported.

**B4. `proxy/lib/` was explicitly rejected two PRs ago; this directive reintroduces it without acknowledgment.** PR #213's round-1 review flagged the phantom `proxy/lib/` as part of blocker B2, and the round-2 resolution confirmed the convention: "no `proxy/lib/` introduced; `image-hash.mjs` lands flat in `proxy/` per existing convention" (`pr-213-round-2-fable.md`, B2 row). Shared helpers live flat: `proxy/helpers.mjs`, `proxy/image-dimensions.mjs`, `proxy/image-resize.mjs`, `proxy/rates.mjs` (verified against current `main`). PR #215 places both new modules in `proxy/lib/` and cites the 2+-consumers rule as if it settled the directory question — it doesn't; it justifies a shared *module*, not a new *directory layer*. Same for `test/lib/`: the test tree is flat (`test/*.test.mjs`, verified). Either move both modules (and tests) to the flat convention, or state explicitly why this PR overturns the #213 resolution — silently re-litigating a settled convention question is how a codebase ends up with both layouts.

**B5. The markers catalog — the load-bearing detection input — has no concrete content.** Detection condition 3 depends entirely on `workflow-markers.mjs`, described as "extracted from binary inspection per `playbook_cc_binary_inspection.md`." The playbook exists and the method is sound, but no actual markers are cited anywhere: `<workflow-agent-context>` and `[workflow-agent]` appear with no binary version, no sha256, no `strings` output — and the reviewer checklist's "catalog reflects the v2.1.170 binary state (cc-watch inspection used as source)" references findings that are not in the directive, the PR, or the playbook. The playbook's own citation discipline requires the binary sha256 for any durable artifact. If the markers are speculative, the feature may detect nothing (or the wrong things) and every downstream test is built on sand. Either seed the catalog in the directive with binary-verified markers (version + sha256 + the matched strings), or restructure: make marker discovery an explicit gating task with the directive's detection logic conditional on its output.

## What Needs Attention

1. **"Additive only, no request mutation" is self-contradictory as written.** Adding headers *is* request mutation, and "harmless, ignored by Anthropic" is asserted without evidence. Resolving B1 the recommended way (ctx.meta, nothing upstream) makes the claim true; if header emission upstream is retained for some reason, it needs default-off until validated against the live API, per the same caution that gated `request_id`.
2. **The activation model doesn't fit the loader.** "`enabled: true` in `extensions.json` for the helper module (always loaded)" — `extensions.json` configures extensions in `proxy/extensions/` by export name (`pipeline.mjs:26-27`); lib modules are imported, not registered, and need no config entry. Meanwhile both named consumers are `enabled: false` by default (`usage-log.mjs:270`, `request-log.mjs:8`; usage-log isn't even present in `extensions.json`), and request-log additionally no-ops without `CACHE_FIX_REQUEST_LOG` set (`request-log.mjs:3,21`). So "default-on in v4.2.0" describes an env-var defaulting to `on` for a derivation with zero active consumers in a default install. State what default-on actually means operationally, and which extension entry (if any) changes in `extensions.json`.
3. **Event-log location and discipline.** `~/.cache-fix-proxy/workflow-derivation-events.jsonl` breaks the established home — every proxy artifact lives under `~/.claude/` (`usage.jsonl`, `quota-status/`, `cache-fix-debug.log`). And "showing the inputs" is underspecified: the marker substring is prompt-derived content, and the derivation inputs border on prompt text. Pin the PII allowlist (session id, marker *name/id* — not matched prompt text — derived ids, timestamp) and rotation (5 MB single-tier per the `bootstrap-defense` precedent, reaffirmed in #213 A6). Small scope doesn't excuse an unbounded JSONL of prompt-derived strings.
4. **Marker false positives from user-controlled content.** Condition 3 scans "system-prompt or first-user-message" — a user message that *quotes* `[workflow-agent]` (e.g., someone discussing this very feature) triggers derivation. Consequence is mild (mis-attributed meter row), but cheap hardening exists: prefer system-prompt-position-anchored matches, and add a negative test for marker-text-in-user-content.
5. **`derived_parent_agent_id` flattens nesting.** `sha256(session_id + "workflow-root")` gives every Workflow agent in a session the same parent, including nested `pipeline()`-within-`parallel()` trees. Probably the right v1 simplification — but say so, since "Workflow tree" language implies structure the parent id doesn't capture.
6. **64-bit truncation.** `slice(0, 16)` matches house precedent (`hashOrgId`, `sessionFilename`) and is fine for per-session attribution, but document that the id is not globally unique (~2^32 birthday bound) so a future cross-user aggregation doesn't silently inherit collision risk.
7. **Catalog maintenance is a manual handoff — say so.** cc-watch's runbook covers *how* to inspect, but there is no automated drift detection for new Workflow sentinels; a CC release that changes the marker silently kills detection (fail-open means the failure mode is "rows quietly lose attribution"). Name it honestly as a manual watch surface, and consider a cheap canary: log (throttled) when condition 1+2 hold but no marker matches — that's exactly the signature of marker drift.
8. **Test plan gaps.** (a) No sessionless case (condition 1 false → no derivation — assert it). (b) No marker-in-user-content false-positive case (item 4). (c) No test that an emitted row validates against the actual meter schema — exactly the test that would have caught B2. (d) The fixture `workflow-parallel-fanout-replay.json` is the first of its kind (`test/fixtures/` contains only `burst-limit-429.json`) — state whether it's a real captured Workflow fan-out or hand-synthesized; for a heuristic detector, a synthetic fixture only proves the heuristic matches the fixture's author's guess. (e) The "3 distinct ids" assertion needs rewriting per B3 regardless.

## Bloat / Non-Functional

- The 80–150 LOC budget is plausible for the two modules plus extension edits *only if* the markers catalog stays small and tests are excluded — but the Files-created list includes two test suites and an integration fixture, which #213's budget round-trip established should be counted honestly. Restate as code-vs-tests split; if the catalog needs dozens of entries the budget is fiction.
- "Persistence of the markers catalog across cache-fix releases" in Out-of-scope is a non-statement — the catalog is source code; source persists across releases by definition. Delete or say what was actually meant (probably: no runtime-updatable catalog).
- The dual header pair (`derived-agent-id` + `derived-parent-agent-id`) doubles the surface for a parent id that is a pure function of session id. If B1 resolves to ctx.meta, consider whether the parent id needs to exist at all in v1 — consumers can derive it.

## Recommendations

1. Rewrite Synthesis around the real pipeline: named extension with an `onRequest` hook runs the derivation (body + headers are both visible there), stashes `{derivedAgentId, derivedParentAgentId, markerId}` on `ctx.meta`; usage-log and request-log read `ctx.meta`. Drop upstream header emission entirely — no claim about Anthropic ignoring headers needed, and "additive only" becomes true.
2. Fix the meter contract: companion meter PR adds `agent_id` + `agent_id_source` (or equivalent) to `MeterRowSchema` as optional fields *first*; cache-fix emission ships default-**off** behind the env-var with the default flip deferred to the release after the meter floor exists — the exact `request_id` v4.1.0→v4.2.0 pattern already documented in `usage-log.mjs`.
3. Re-derive the id with a per-leg discriminator sourced from inside the Workflow context block (whatever binary inspection confirms is there), and decide the tools-churn question (harden the signature or document the split-id failure mode).
4. Move both modules and tests to the flat layout per the #213 resolution, or explicitly argue the convention change in the directive.
5. Seed `workflow-markers.mjs` content in the directive with binary-cited markers (CC version + sha256 + matched strings), or gate the directive on a named discovery task.
6. Relocate the event log under `~/.claude/`, pin PII allowlist + rotation, and add the no-marker-matched drift canary.

## Bottom Line

The motivation is sound, the derived-not-authoritative posture is exactly right, and the self-retiring design is the kind of upstream-respecting fix this proxy does well. But the directive's mechanics fail verification at every load-bearing joint: the headers it synthesizes cannot reach the wire through the existing pipeline and nothing owns the derivation; the meter field it claims already exists does not, and default-on would break every unpatched meter install; the derived id cannot pass the directive's own three-distinct-ids test; the module home contradicts a convention settled in PR #213; and the marker catalog the whole detection rests on has no verified content. All five are fixable in one revision pass — and B1's fix (ctx.meta instead of header emission) simplifies the design rather than complicating it. Fix B1–B5, tighten the activation-model description, and this is approvable in round 2.
